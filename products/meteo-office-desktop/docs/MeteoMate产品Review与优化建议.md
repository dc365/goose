> Review 对象：`dc365/goose` 仓库 `products/meteo-office-desktop`（MeteoMate Desktop 0.2.0 Beta）
> Review 日期：2026-07-26
> 范围：仅产品层（products 目录），Goose 内核不做修改、不在本次修改建议范围内
> 方法：克隆仓库 → 静态代码审查（主进程 / 渲染层 / 样式 / Manifest / 文档 / 测试）→ 实际启动 SkillHub 服务与 Electron 应用（演示模式）→ 逐界面截图走查 → 运行 `npm run check` 全部测试
>
> **2026-07-26 更新**：高价值修复包已在分支 `agent/meteomate-ux-fixes` 完成并实机验证（窗口控制、排队发送、输入保护、场景 SVG 图标、语音死入口、模型去配置入口、文档对齐），详见文末「九、修复实施记录」；相关条目已标注 ✅。另修正初版一处误判：`styles/app-*.css` 经 `@import` 被 `styles-app.css` 引用，并非死文件（见 P1-5 修订）。
> **说明**：SkillHub 为服务端部署的管理后台，非桌面端本地依赖，初版 P0-1（首启需本地 SkillHub）按既定设计保留，不再列为问题。

## 一、总体结论

MeteoMate Beta 的完成度和工程质量**明显高于一般内部工具**：Manifest 驱动的信息架构、ACP/Headless/Mock 三级运行时降级、审批模式默认开启、SkillHub 版本签名与灰度治理、27 个契约/单元测试、完善的文档体系（12 篇设计文档）都是亮点。界面视觉统一、中文业务文案专业、空状态与演示模式标识克制诚实。

主要优化空间集中在四类：

| 维度 | 核心问题 | 影响 |
| --- | --- | --- |
| 产品 | 核心价值闭环（气象数据 → 诊断 → 稿件）尚未接通，三个差异化 MCP 仍为 planned | 产品差异化价值未落地 |
| 产品 | 文档（PRODUCT_BETA）与实现已明显漂移（三栏任务台、"更多"入口等） | 新人按文档理解产品会产生偏差（✅ 已对齐） |
| 设计 | 无深色模式；场景图标依赖 Unicode 符号（✅ 已 SVG 化）；样式文件组织混乱 | 视觉一致性与可维护性 |
| 界面 | 运行中无法排队指令（✅ 已修复）；流式期全量重绘打断输入与滚动（✅ 已加保护） | 长任务下的交互效率与渲染性能 |

**结论：可以进入小范围真实用户试用。初版提出的 4 项 P0 中，跨平台窗口控制、消息排队两项已完成修复并实机验证；SkillHub 为服务端部署属既定设计；剩余 P0 为 0.3 里程碑的气象数据闭环。**

## 二、做得好的地方（建议保持）

### 2.1 产品与工程

- **内核隔离干净**：近 50 个提交全部落在 `products/meteo-office-desktop/` 与一条 CI workflow，未触碰 `crates/`、`ui/` 等 Goose 内核目录，上游同步策略成立。
- **运行时三档降级诚实透明**：ACP 优先 → Headless 只读降级 → 演示模式；演示输出明确标注"MeteoMate 演示模式 / 当前尚未调用真实 Goose 模型"（见截图 08），不伪装成真实模型输出，这在政务/业务场景是关键的信任设计。
- **安全默认值正确**：`GOOSE_MODE=approve`、只读专家默认关闭文件工具、Headless 禁止文件工具、进程参数数组启动不经 Shell、Renderer 沙箱 + `contextIsolation`、CSP `script-src 'self'`、密钥 `0600` 且独立 `GOOSE_PATH_ROOT`、不读系统钥匙串。
- **审批交互完整**：权限卡片提供"允许一次 / 本会话允许 / 拒绝"三档（`renderPermissionCard`），符合 ACP 语义。
- **SkillHub 治理设计完整**：同版本不可变、Ed25519 签名、草稿/发布/弃用状态机、组织策略下发（含自动压缩阈值 50%–95%）、审计记录——管理后台实测可用（见截图 12）。
- **测试与契约**：27 个测试文件 + JSON Schema 契约（`schemas/`），`check:syntax` 与 smoke/harness 测试本次实测全部通过。
- **Markdown 渲染做了净化**：`marked` + DOMPurify（并显式禁用 `style/iframe/form` 等标签），`innerHTML` 使用点基本都有前置 `sanitize`。

### 2.2 界面与文案

- 空状态文案质量高（"让每次研判有上下文，让每份成果有来处"、"接入第一份气象资料"），并直接给出行动按钮，见截图 04/05/06。
- 模型状态在输入框上直接展示（"模型不可用"徽标），上下文占用与自动压缩状态可见，符合"可核验"的产品哲学。
- 中文业务术语准确（形势分析、槽线、切变线、时次、落区），专家/场景/自动化模板的气象领域感强。
- 图标（深蓝底 + 蓝色等值线 + 隐含 M 字母）与"气象 + 智能"的定位契合，辨识度高（见截图 00）。

## 三、产品层问题与建议

### P0-1 ~~首次运行门槛过高~~（按既定设计保留：SkillHub 为服务端部署）

**说明（2026-07-26 更新）**：经与产品方确认，SkillHub 是部署到服务端的管理后台，桌面端登录服务端账号是目标形态，本地首启依赖并非设计缺陷。本节保留作为 onboarding 体验的参考建议，不再计为问题：

1. 桌面端可在检测到 SkillHub 不可达时给出明确引导（服务地址配置入口 / 离线试用说明），而非只有一个无解释的登录框；
2. 团队部署场景下，可提供"组织服务地址"的首次运行向导，缩短业务用户从安装到登录的路径。

### P0-2 核心价值闭环尚未接通，差异化能力都还是 `planned`

**现状**：产品定位是"气象业务智能工作空间"，但最能体现差异化的三个 MCP——`weather-data`、`weather-diagnosis`、`gis-map`（气象数据中心、天气诊断算法、GIS 制图）在 `manifests/capabilities.js` 中均为 `status: 'planned'`；PRODUCT_BETA 定义的"第一条真实业务闭环"（形势分析 → 写稿 → DOCX/PDF）目前只能在演示模式下看到流程描述。

实测演示模式的输出（截图 08）本身设计得很好（明确列出建议执行计划和缺失依赖），但也反衬出：**当前用户实际能用的是"通用 Agent + Office 成果物 + 浏览器/桌面自动化"，气象部分只有 Skill 提示词，没有数据工具。**

**建议**：

1. 把 0.3 里程碑的 `weather-data-mcp` 收窄到一个最小可演示形态：先支持"本地 JSON/CSV + 一个公开 API 源"，让形势分析专家能在真实任务里产出一次带数据来源的回答；
2. 在工具中心为 `planned` 状态的卡片增加"订阅上线通知"或 Roadmap 说明，避免用户反复点"配置工具服务"才发现不可用；
3. 演示模式的"建议执行计划"可以升级为一键跳转："缺少 weather-data-mcp，[查看接入指南]"，把限制转化为转化路径。

### P1-1 自动化只能在应用打开期间运行，但没有常驻形态

**现状**：文档明确"调度只在 MeteoMate 打开期间运行"，但应用没有 Tray（托盘）常驻（`main.cjs` 中无 `Tray`），窗口关掉调度就停。对"每日天气形势摘要（每天早间）"这类模板，用户很容易误以为设好了就会自动跑。

**建议**：短期在自动化创建页和模板卡上加显著提示"需保持 MeteoMate 运行"；中期加 Tray 常驻与"已完成 N 次定时任务"的徽标反馈；长期按路线图交给 Remote Worker。

### P1-2 单用户 Beta 却先建了完整的"管理员/组织/审核"体系，路径上用户角色错位

SkillHub 后台（用户管理、策略下发、审计、灰度）是按团队版 0.5 的规格建的，而 Beta 的目标用户是"一个用户围绕一个项目持续工作"。这导致：普通业务用户首次登录看到的是"系统管理员"身份（截图 01 底部、截图 11），信息架构里也提前出现了"空间""我的专家/同步/发布草稿"等团队概念。

**建议**：不删功能，但做身份降噪——桌面端按角色收敛入口（个人用户默认隐藏发布管理、组织策略入口），把"系统管理员"字样改为对用户有意义的"本机管理员"等；团队概念（空间）在单用户场景给出"未来可用"的轻提示而非空列表。

### P2-1 文档与实现漂移 ✅ PRODUCT_BETA 已对齐

| 文档描述 | 实际实现 |
| --- | --- |
| PRODUCT_BETA：任务界面三栏（左：专家/项目/权限/会话，右：执行计划/工具活动/审批/成果物） | 实际为单栏对话流，计划/思考/工具以消息内折叠区呈现（"已完成 1.4s ⌄"），成果物以画廊内嵌 |
| PRODUCT_BETA：信息架构含"更多" | 侧边栏实际为：新建任务 / 助理 / 项目 / 资料库 / 专家·技能·工具 / 自动化，无"更多" |
| README：`goose serve --platform desktop` | 以代码为准，建议确认参数与上游一致性 |

建议每个里程碑收尾时跑一次"文档对齐"，或在文档头部加"实现状态"标注。

### P2-2 目录与产品命名不一致

产品叫 MeteoMate，目录是 `products/meteo-office-desktop`（README 解释为避免无意义 Diff，可理解）。建议在正式独立仓库/0.3 里程碑时统一为 `meteomate-desktop`，并同步 `package.json`、Bundle ID（现为 `com.meteomate.desktop`，已是目标形态）。

## 四、设计层问题与建议（视觉与前端架构）

### P0-3 窗口控制仅适配 macOS，Windows/Linux 无法关闭窗口 ✅ 已修复

**现状**：`BrowserWindow` 使用 `titleBarStyle: 'hiddenInset'`，渲染层实现了拖拽区（`-webkit-app-region: drag`），但**全代码库没有任何最小化/最大化/关闭按钮**（已全量检索确认）。在 macOS 上 `hiddenInset` 保留红绿灯按钮没有问题；在 Windows/Linux 上该值等价于 `hidden`——用户将没有任何窗口控制按钮，只能靠任务栏右键或快捷键。打包脚本也只有 `package:mac`。

**建议**：渲染层补一组窗口控制按钮（Windows/Linux 显示，macOS 隐藏），主进程加 `window:min/max/close` IPC；或短期内在 Windows/Linux 构建时退回原生标题栏。若团队版目标包含 Windows（气象局业务环境大概率是 Windows），这条必须从 P2 提到 P0。

### P1-3 无深色模式

`styles-base.css` 硬编码 `color-scheme: light`，全部 12 个样式表无一份深色变量。气象业务有夜间值班场景，且 macOS 深色环境下浅色窗口较刺眼。建议：把现有 CSS 变量（已有良好基础：`--bg/--panel/--text/--line` 等语义化命名）扩展为 `light/dark` 双套，跟随系统 + 设置项手动覆盖。

### P1-4 场景与业务图标依赖 Unicode 符号与单字头像 ✅ 场景图标已 SVG 化

- 场景图标用的是 `◒ ϟ ✦ ⌁` 这类 Unicode 符号（`manifests/scenes.js`），在不同平台字体下渲染不一致（实测 Linux 下部分符号发虚/偏小，见截图 07）；
- 专家/技能头像为单汉字（形、雨、雷、稿、办、数），风格统一但信息密度低，且 SkillHub 后台与桌面端头像渲染逻辑各自实现。

建议：统一为 SVG 图标体系（现有 `icon()` 已有内联 SVG 基础），气象场景可用等值线/雷达/探空等专属图形；单字头像保留为兜底。

### P1-5 ~~死样式文件约 81KB~~（已修正）→ 样式组织需要整理

**修正**：`styles/app-1.css ~ app-4.css` 并非死文件——`styles-app.css` 头部通过 `@import url("styles/app-N.css")` 引用了它们（初版仅检索了 HTML/JS，遗漏 CSS 引用链，特此更正）。真正的问题是**组织**：

- 根目录 12 份 `styles-*.css` + `styles/` 下 4 份无语义命名的 `app-1..4.css`（其中 app-4 达 64KB），新成员很难判断该往哪里写样式；
- `styles/app-2.css` 中仍保留 MVP 时期三栏任务布局（`.task-layout` 268px/326px 网格、`.task-context-panel`、`.inspector-panel`）等已不再被渲染层使用的规则，属于真正的死规则。

建议：按 `base / layout / components / views` 重命名合并；用构建期或人工审计清理未被引用的历史规则（可借助 coverage 工具按界面走查导出）。

### P2-3 其他视觉细节

- **字体**：字体栈首选 Inter，但产品未内置 Inter 字体文件，实际渲染取决于用户系统；中文走 PingFang/雅黑回退，macOS/Windows 问题不大，Linux 目标用户需确认 Noto Sans CJK 兜底效果。
- **侧边栏固定 330px + 最小窗口 1220×760**：在 1280px 宽的老式业务机上，主内容区仅剩约 890px，工具中心三列卡片会偏挤（样式表已有 media query 做部分适配）。建议侧边栏增加可拖拽宽度或更积极的折叠档位（现有 72px 折叠态可在此基础上增加"半折叠"）。
- **品牌一致性**：应用图标为深蓝底，界面主色为浅灰白 + `#4b75f2` 蓝，整体协调；但品牌 Manifest 的 `--brand: #2f343b`（近黑）与图标深蓝（约 `#1c2333`）不完全一致，建议在 `brand.js` 中沉淀标准色板供 CSS 变量对齐。
- **标题栏 42px 占位在所有平台生效**：Windows/Linux 若退回原生标题栏，记得联动调整 `--window-titlebar-height`。

## 五、界面与交互层问题与建议

### P0-4 运行中输入框整体禁用，无法排队下一条指令 ✅ 已修复

**现状**：任务运行期间 `<textarea id="task-prompt" disabled>`、发送键禁用（截图 08 状态）。用户看完一段流式输出后想补充"再查一下 850hPa"必须等整个任务结束或先取消。

**建议**：参考主流 Agent 产品，允许运行中继续输入并"排队"（发送键变为"排队/插队"或出现"待发送"气泡）；至少允许输入草稿（当前草稿机制 `draftPrompt` 已实现持久化，只需解禁输入框）。这是任务型 Agent 最高频的交互诉求，建议排 P0。

### P1-6 流式期间每 80ms 全量 `innerHTML` 重绘 🔶 已缓解（输入保护），局部渲染重构仍建议

**现状**：`scheduleRuntimeStreamCommit` 以 80ms 间隔调用 `render()`，而 `render()` 是 `appElement.innerHTML = 全量模板` + `bindEvents()` 全量重绑。后果：

- 长会话下每次重绘重建整棵 DOM 树，CPU 占用与内存抖动随消息数线性增长；
- 重绘会清除用户的文本选区、hover 状态与滚动中的惯性；
- 输入框因运行中被禁用才侥幸避开了"输入被打断"，一旦按上条建议解禁输入框，**中文输入法（IME 组合态）会被每 80ms 的重绘直接打断**，两个改动必须配套做。

**建议**：渲染层做最小化更新——消息流区域按 `message.id` 做 keyed 局部 DOM 更新（或引入轻量模板 diff，如 lit-html / morphdom）；全量 `render()` 只用于视图切换。这两个文件（`renderer-core.js` 3008 行 / `renderer-actions.js` 3663 行）已足够大，局部更新改造可顺带做模块拆分。

### P1-7 演示模式/降级模式的下一步引导可以更产品化 🔶 已加入口，接入指南待 0.3

演示模式结果页（截图 08）已有依赖说明，但全是文字。建议把"请先完成 Goose Provider 配置"做成可点击的设置跳转卡片（设置 → 模型已存在对应页面），把"演示模式"从免责声明变成 onboarding 漏斗。

### P2-4 语音输入是"死入口" ✅ 已隐藏

输入框有语音按钮，`aria-disabled="true"` + tooltip"功能即将提供"。死入口在专业工具里可以接受，但更稳妥的做法是默认隐藏、能力就绪后再出现——否则用户每发一条消息都会看到一次"不可用"。

### P2-5 无障碍覆盖不均衡

`renderer-core.js` 有 84 处 aria/role 标注（快捷面板 `role="listbox"`、Esc 关闭等都有），但 `renderer-actions.js` 仅 3 处、`capability-center/` 多数文件为 0；图标化按钮（如返回键 `font-size: 0`）依赖 aria-label 兜底，建议补齐能力中心各弹窗的标签与焦点管理（modal 已标 `aria-modal`，焦点圈闭未验证）。`prefers-reduced-motion` 已适配（8 处），值得保持。

### P2-6 其他交互细节

- 任务列表/空间列表在侧边栏固定占位（"任务 (0) 还没有任务"），空态可以更紧凑，把空间留给导航；
- 设置页"返回应用"在左上，与主应用导航习惯一致，但设置内无搜索，项多了之后建议加分组锚点；
- 快捷面板（@ 引用文件、/ 调技能）已实现键盘操作（↑↓/Enter/Tab/Esc），体验完整，建议在输入框 placeholder 之外增加一次性的引导提示。
