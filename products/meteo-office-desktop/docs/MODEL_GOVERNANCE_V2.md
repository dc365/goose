# MeteoMate 第二期：组织模型治理落地说明

本文对应已经落地的第二期实现，不是未来方案占位。它说明管理员怎样登记模型、桌面端怎样使用目录、凭据保存在哪里，以及演示时如何证明配置真实有效。

## 1. 本期交付范围

第二期把“每台电脑各自填写一个 OpenAI Compatible 地址”改造成组织可管理、用户仍可安全使用的模型目录：

- 后台统一登记提供商、协议、完整请求路径、流式策略和模型能力；
- 明确区分 `chat_completions` 与 `responses`，不再只依赖 URL 猜测；
- 管理员可限制组织、角色或用户能使用的提供商与模型；
- 可要求桌面端只显示已经完成真实验证的模型；
- 桌面端同步有效目录并过滤模型选择，不允许绕过策略启动被禁用模型；
- 验证状态、操作者和时间进入审计，但 API Key、测试提示词、响应正文和图片不进入 SkillHub。

## 2. 请求协议如何确定

后台把服务地址和协议拆开保存。显式填写 `endpointPath` 时，桌面端使用 `baseUrl` 的 Origin 加该路径形成最终地址，避免 `/api/v3` 被重复拼接；未填写时再从 Base URL 和协议推导路径：

| 场景 | presetMode | protocol | 常用请求路径 | 流式建议 |
|---|---|---|---|---|
| 通用 OpenAI 兼容服务 | `openai-compatible` | `chat_completions` | `/v1/chat/completions` | `auto` 或 `on` |
| OpenAI Responses 兼容服务 | `openai-compatible` | `responses` | `/v1/responses` | 按供应商文档 |
| 火山方舟 Ark / 豆包 Responses | `volcengine-ark` | `responses` | `/api/v3/responses` | 当前兼容策略使用 `off` |

`/v1/chat/completions` 接收 `messages`，输出以 `choices[].message` 为主；Responses 接收统一的 `input` 内容块，文本、图片、工具调用和推理事件都在响应项/事件流中表达。二者不是只换一个 URL，序列化请求、流式事件解析和工具调用回传都不同，因此必须在提供商连接上明确记录协议。

选择规则：先以供应商当前官方文档为准，再用桌面端真实探测确认文本、流式、工具、图片和推理能力。后台的“记录验证”只登记探测证据，不从浏览器直接调用模型。

## 3. 数据与安全边界

模型目录保存在：

```text
<skillhub-data>/models/model-catalog.json
```

文件以原子方式写入并使用 `0600` 权限。目录中可以保存：

- 连接地址、请求路径、协议与流式策略；
- 模型 ID、显示名、能力声明和 token 上限；
- 凭据模式与外部密钥引用；
- 验证状态、检查项、操作者和时间。

目录中禁止保存明文密钥。凭据模式如下：

- `local`：API Key 由每位用户在桌面端填写，保存在该用户独立 Goose 目录的 `config/secrets.yaml`，权限为 `0600`；
- `secret_ref`：SkillHub 只保存 `env://`、`vault://`、`secret://` 或 `k8s://` 引用；
- `none`：连接不需要鉴权。

普通用户接口会移除 `secretRef`，只返回 `credentialConfigured` 布尔值。管理员接口能够看到引用名称，仍看不到实际密钥。

## 4. API 与策略

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/v1/me/model-catalog` | 返回按当前用户有效策略过滤后的目录 |
| `GET` | `/v1/admin/model-providers` | 管理员读取完整目录 |
| `PUT` | `/v1/admin/model-providers/{id}` | 新建或替换提供商 |
| `DELETE` | `/v1/admin/model-providers/{id}` | 删除未被策略引用的提供商 |
| `POST` | `/v1/admin/model-providers/{id}/verification` | 登记真实探测结果 |

策略新增：

- `allowedProviderIds`：允许的提供商 ID；空数组表示不额外限制；
- `allowedModels`：允许的 `provider/model`；空数组表示不额外限制；
- `requireVerifiedModels`：为 `true` 时只下发验证状态为 `verified` 的模型。

策略写入时会校验提供商和模型是否存在、是否启用。被任何组织、角色或用户策略引用的对象不能直接停用或删除，避免已发布策略悬空。

## 5. 桌面端行为

登录或刷新组织信息时，桌面端并行读取 `/v1/me/policy` 和 `/v1/me/model-catalog`。已有旧版 SkillHub 没有目录接口并返回 404 时，桌面端保持向后兼容；一旦目录非空，它就成为组织模型的权威来源。

桌面端会：

1. 只保留目录和策略共同允许的提供商、模型；
2. 在要求验证时移除未验证模型；
3. 使用组织登记的协议、路径、流式策略和能力元数据；
4. 保留本机 API Key，不用后台响应覆盖本机秘密；
5. 对组织托管提供商锁定连接和模型结构，只允许用户维护本机凭据；全新电脑会先显示目录占位项，用户首次保存密钥时自动创建本地 Goose 连接并绑定组织 Provider ID；
6. 离线时使用上一次安全缓存，并继续执行同一组限制。

## 6. 演示验收流程

1. 以管理员登录 `http://127.0.0.1:8088/admin/`，打开“模型目录”。
2. 新建 `doubao`，选择“火山方舟 Ark / Responses / 关闭流式”，填写模型 `doubao-seed-2-1-pro`。
3. 在桌面端填写本机 API Key，执行文本、工具、图片和推理探测。
4. 回到后台登记该次真实探测的结果；不要用构造结果冒充真实联网验证。
5. 在“策略”中勾选 `doubao`、对应模型，并开启“仅允许已验证模型”。
6. 使用普通用户登录桌面端，确认只显示该模型，且连接页显示组织托管、本机凭据。
7. 在后台暂时把模型验证登记为失败，刷新桌面端，确认模型不再可选；恢复验证后再次出现。
8. 尝试删除仍被策略引用的提供商，应收到 `409`，证明策略引用保护生效。

演示数据只用于展示配置和流程时，应明确标注“演示”。模型验证状态必须来自一次实际请求；没有实际请求时保持 `untested`，不能编造为 `verified`。

## 7. 当前边界与后续工作

- `secret_ref` 已完成安全数据模型和 API 边界，具体 Vault/Kubernetes Secret 解析应由部署环境或后续服务端执行器接入；
- 当前目录为适合内网试点的原子 JSON 存储，规模扩大后可迁移至数据库；
- 后台只记录探测结果。若后续需要后台主动探测，应单独设计出网策略、凭据代理、请求内容脱敏和审计，不应让浏览器持有组织密钥；
- 每个供应商升级 API 版本时，应先更新目录并重新完成能力探测，再允许进入生产策略。
